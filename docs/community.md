# 커뮤니티와 인증 연결

## 확정된 제품 방향

- 열람과 지구본 탐색은 로그인 없이 가능.
- 댓글 작성에는 본인 인증과 국적 인증을 모두 요구.
- 댓글에는 닉네임과 **작성 시점에 인증된 국적**을 표시. 저장 구조는 복수 국적을 지원하지만 현재 Didit 흐름은 제출한 여권에서 확인한 국적 하나만 반영.
- 실명, 생년월일, 신분증 이미지·번호, 이메일은 댓글이나 공개 프로필에 저장하지 않음.
- 국적을 정보의 진위나 의견의 신뢰도를 판단하는 점수로 사용하지 않음.
- 감상과 사실 설명을 구분하고, 출처 링크·스포일러 표시·신고를 지원.

## 데이터 경계

`profiles`는 닉네임과 공개에 동의한 인증 국적만 포함합니다. 이용자가 직접 수정할 수 있는 열은 `display_name`뿐입니다.

`private.verifications`는 인증 사업자, 여권 발급국과 번호를 서버에서 HMAC 처리한 값, 확인 시각, 확인된 국적 코드, 국적 공개 동의 시각, 만료 시각을 보관합니다. 일반 이용자와 익명 방문자는 이 테이블을 읽거나 수정할 수 없습니다. 같은 여권의 중복 계정 사용은 UNIQUE 제약으로 차단합니다. 여권 갱신·다른 여권이나 사업자 간 동일인 판별은 보장하지 않습니다.

`comments.author_nationality_codes`는 DB 트리거가 검증 레코드에서 복사합니다. 브라우저는 이 열을 지정할 수 없습니다. 따라서 프로필이 나중에 바뀌어도 당시 댓글의 표시는 유지됩니다. 계정 삭제 시 댓글과 인증 레코드는 함께 삭제됩니다. 국적 공개 동의 철회 시 인증 레코드를 지우고 이전 댓글을 숨기며 댓글의 국적 코드를 비웁니다. 뒤늦은 인증 응답은 권한을 복구하지 못합니다. 다시 인증하더라도 이전 댓글은 자동으로 공개되지 않습니다.

RLS는 로그인 계정, 본인 확인, 국적 확인, 만료, 차단을 확인합니다. 프런트엔드의 버튼 비활성화는 보조 안내이며 권한 검사는 데이터베이스가 수행합니다. 같은 작성자가 30초 안에 재작성하는 것을 제한하고 작성자별 잠금으로 동시 요청도 직렬화합니다. 삭제 후 재작성 등의 모든 남용을 막는 전체 rate limiter는 아니므로 공개 서비스에서는 별도의 요청 단위 제한을 추가할 수 있습니다.

## Didit 어댑터: 구현 완료, 실제 연결 대기

`identity-session` Edge Function은 Supabase에서 로그인 토큰과 이메일 확인을 검증하고 명시적 동의를 받은 뒤 인증 세션을 만듭니다. 서버가 만든 불투명한 시도 ID로 계정과 Didit 세션을 묶습니다. 브라우저가 보낸 사용자 ID나 인증 결과는 사용하지 않습니다.

`didit-webhook`은 전체 본문의 V2 HMAC, 본문·헤더 타임스탬프 일치와 5분 유효기간을 확인한 뒤 Didit API에서 결과를 재조회합니다. 정확한 워크플로·세션·시도 ID, 실제 환경, 여권 문서 확인·얼굴 생존 확인·얼굴 일치의 승인, 유효기간을 모두 확인합니다. 샌드박스 결과는 권한을 부여하지 않습니다. 발급국·IP·예상값으로 국적을 채우지 않고 문서의 nationality 값만 사용합니다.

`private.identity_sessions`는 계정 연결·동의 시각·진행 상태·개인 인증 URL을 비공개로 보관하며 종료 시 URL을 지웁니다. `private.identity_events`는 이벤트 ID와 처리 시각만 저장합니다. 원본 사진·여권 번호·실명·전체 응답은 DB나 애플리케이션 로그에 저장하지 않습니다. Didit 자체의 원본 처리·보관·삭제 정책은 별도로 안내합니다.

새 인증은 계정별 2분 간격·24시간 3회, 사이트 전체 UTC 월 450회로 제한합니다. 이것만으로 업체 과금을 완전히 막는 것은 아니므로 유료 기능·자동 충전은 켜지 않고 업체 사용량도 확인합니다. 결과 재조회는 15초 간격입니다. 웹훅은 이벤트 중복·역순·철회 이후 응답을 방어합니다.

현재 업체 계정·워크플로·서버 자격 증명 연결과 실제 여권을 이용한 통합 검증이 남아 있습니다. 공개 화면과 서버 모두 기본적으로 비활성화됩니다. 설정 및 개방 조건은 [인증 연결 안내](identity-verification-setup.md)를 따릅니다.

## Supabase 보안 점검

포함된 마이그레이션의 권한 구조: 인증을 기록하는 네 RPC는 service_role만 실행할 수 있고, 일반 계정은 자신의 상태 조회와 동의 철회만 실행합니다. private 테이블은 RLS가 켜져 있고 일반 사용자 정책이 없어 접근이 거부됩니다.

- [RLS Enabled No Policy](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy): private 네 테이블의 의도적인 기본 거부 설정입니다.
- [Signed-In Users Can Execute SECURITY DEFINER Function](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable): 본인 상태·권한 조회와 철회에 필요합니다. auth.uid()로 대상이 고정되며 search_path는 비워두었습니다. 다른 계정 접근 거부를 SQL 테스트로 검증합니다.

## 신고 운영

인증된 이용자는 다른 사람의 보이는 댓글을 한 번 신고할 수 있습니다. 신고 이유는 신고자와 운영자만 볼 수 있습니다. 운영자는 DB에서 신고를 검토하고 `comments.status='hidden'`으로 숨기거나 `private.blocked_users`에 계정을 추가할 수 있습니다. 운영자 UI와 알림 전송은 아직 없습니다. 허위정보나 의견 차이를 국적만으로 판정하는 자동 처리는 없습니다.

## 검증 범위

PGlite를 이용해 실제 PostgreSQL 권한과 RLS를 검사합니다. 테스트의 가짜 인증 레코드는 테스트용 메모리 DB 안에서만 만들어집니다. 앱 화면, 로컬 저장소, 실제 Supabase 프로젝트에는 가짜 인증을 기록하지 않습니다.

외부 서비스 연결 후 이메일 로그인, 인증 사업자별 성공/실패/재전송, 세션 바꿔치기, 국적 표시, 동의 철회, 만료, 신고 검토를 다시 통합 검증해야 합니다.
